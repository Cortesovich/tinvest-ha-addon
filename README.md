# TInvestBot

Telegram-бот для ИИС в Т-Инвестициях (Tinkoff / T-Bank) на **чистом REST API**:
read-only отчётность (баланс, доходность XIRR, купоны, сроки погашения, подбор
бумаг) и консервативная **автопокупка надёжных облигаций**. Данные бот отдаёт в
витрину Mini App (Cloudflare Worker) и питает отдельный модуль скоринга.

Репозиторий раньше был **аддоном Home Assistant OS**; сейчас проект на паузе и
переезжает на Ubuntu Server как обычный процесс. HA-обвязка (аддон, Supervisor,
образы ghcr) снята с эксплуатации — см. раздел «Миграция».

> **Внутреннее «завещание» — в [`CLAUDE.md`](./CLAUDE.md)** (в публичный репозиторий
> не пушится). Там то же знание плюс приватные детали: id счёта, chat-id, точные
> имена секретов, инвентарь накопленных данных. Этот README — обезличенная
> версия того же знания, чтобы оно жило в самом репозитории.

## Что это и как устроено

Бот ходит в T-Invest напрямую по REST (`https://invest-public-api.tbank.ru/rest/<Service>/<Method>`),
без официального SDK (причина — ниже). Стек намеренно минимальный:
`requests` + `python-dotenv` + `PyYAML` + `tzdata`.

Основные команды: `/balance`, `/income` (XIRR с учётом вычета), `/coupons`,
`/maturity`, `/topbonds`, `/topstocks`, `/reinvest` (облигации + покупка по кнопке),
`/deposits`, `/accounts`, `/export` (владелец), `/help`. Плюс автопокупка облигаций
по расписанию.

Экспорт формирует несколько обезличенных снимков и пушит портфель в витрину.
Отдельный модуль скоринга (обёртка `build_scoring/app/scoring_runner.py` вокруг
пакета `tinvest_scoring`) считает рыночный профиль по MOEX ISS и публикует его в
витрину отдельным маршрутом.

Доступ ролевой: **Владелец** — полный (включая покупки и `/export`); **Наблюдатель**
— только чтение. Списки chat-id — в рантайм-конфиге (значения в `CLAUDE.md`).

## Требования окружения (критично, переезжает на Ubuntu)

**1. Российский IP обязателен.** T-Invest API пускает только с российского IP,
поэтому бот и живёт дома на Pi. Ubuntu на том же Pi = тот же RU-IP — ОК. Зарубежный
VPS (в т.ч. хост криптоконтура) для T-Invest **не годится** — это и есть причина,
почему контуры разнесены на два хоста.

**2. Russian Trusted CA (НУЦ Минцифры) — это НЕ свойство HA, а свойство API.**
С 2025 Т-Банк перевёл API на TLS НУЦ Минцифры и **отключил старый хост**
`invest-public-api.tinkoff.ru`. Рабочий адрес — `invest-public-api.tbank.ru`, его
сертификат подписан УЦ Минцифры, которого нет в `certifi`, поэтому без рос. корня
падает `SSLError: self-signed certificate in certificate chain`.

- В репозитории `build/russian_trusted.pem` = Russian Trusted Root CA + Sub CA
  (RSA-2022), проверены через `openssl`.
- Бандл = `certifi` + `russian_trusted.pem`, подкладывается через переменные
  окружения `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE`. **Проверка TLS не отключается**
  (`verify=False` не используется) — просто добавлен доверенный корень.
- В `tinvest_client.py` хост `tbank.ru` стоит первым, `tinkoff.ru` — запасным.
- **⚠️ Sub CA действует до 06.03.2027.** При истечении/смене цепочки — обновить
  `russian_trusted.pem` и перезапустить.
- **На Ubuntu:** добавить рос. корень в системный trust store (или тот же
  `REQUESTS_CA_BUNDLE`). Без этого API молчит — это первое, что сломается на новом
  хосте.

## API Т-Банка: живые грабли (все переезжают)

- **`MoneyValue`/`Quotation` = `{units: СТРОКА (целая часть), nano: дробь ×1e-9}`.**
  `units` парсится как `int`: 63.75 приходит как `units:"63", nano:750000000`, а
  **не** `units:"63.75"`. Классическая ошибка в фикстурах — брать дробь из `units`.
- **Цена облигации** приходит в % номинала: `руб = price/100 × nominal`; НКД —
  отдельно (`aciValue`).
- **`market_value` считается только из текущей цены, никогда из средней цены
  покупки** (иначе это не рыночная оценка).
- **Плавающие купоны:** у необъявленных будущих периодов `payOneBond = 0` — у
  флоатера нет единой «ставки». Берём ближайший **объявленный** купон
  (`payOneBond > 0`), иначе `null`.
- **Прямого поля «годовая ставка купона, %» у облигации НЕТ** — деривируем:
  `payOneBond × couponQuantityPerYear / nominal` (равномерный график) либо
  day-count по `couponStartDate`/`couponEndDate` (неравный период).
- **Нет исторической стоимости портфеля** (NAV на прошлую дату). Поэтому честный
  trailing-12m XIRR без собственной истории NAV построить нельзя → он отдаётся как
  `null`. Появится, только если начать копить дневной NAV самим.
- **Нет надёжного прямого поля эмитента** (`issuer_name`) → `null`, из названия не
  гадаем.
- **`PostOrder` для лимитной заявки по облигации требует `priceType:
  "PRICE_TYPE_POINT"`** (есть в актуальном `.proto` `RussianInvestments/investAPI`,
  но **отсутствует** в устаревшем контракте на `tinkoff.github.io`). Цена — в
  пунктах (% номинала), округление вверх до `minPriceIncrement`.
- Используемые методы: `GetAccounts`, `GetPortfolio`, `GetOperationsByCursor`,
  **`BondBy`** (именно `BondBy`, не `GetBondBy`), `GetBondCoupons`, `Bonds`/`Shares`
  (статус `INSTRUMENT_STATUS_BASE`), `GetLastPrices`, `GetTradingStatus`,
  `OrdersService/PostOrder`, `GetAssetFundamentals`.
- **`GetAssetFundamentals`:** активы батчами **≤ 90** за вызов; `peRatioTtm` бывает
  битым у префов/банков (отсюда нижний порог `stock_min_pe`).
- **REST, не SDK, намеренно:** пакет `tinkoff-investments` в целевой сети не
  ставится — прокси подсовывает pip-заглушку на любой пакет со словом «tinkoff».
  Поэтому только прямой REST; таймзона — фолбэк Москвы (UTC+3).

## Почему ключевые решения приняты так (причины, не механика)

- **Автопокупка — только облигации, только лимитками, по расписанию, с лимитом
  концентрации.** Это реальный ИИС, подход консервативный.
  - **Лимитки, а не маркет** — защита от проскальзывания. Цена = последняя × (1 +
    `limit_buffer_pct`), вверх до шага цены. Если заявка не исполнилась сразу —
    статус NEW, «принята, лотов 0», висит в стакане: это **норма, а не ошибка**.
  - **Концентрация** ≤ `bond_max_issuer_pct` на одного **корпоративного** эмитента
    (с учётом уже купленного); **ОФЗ без лимита** (госбумаги — эталон надёжности).
    Фаза «по 1 лоту» лимит игнорирует, чтобы малый бюджет всё равно брал топ-бумагу.
  - **Расписание** по будним опорным дням в первой половине дня, при свободных
    средствах выше порога, не чаще раза в день (дата-гейт в файле). Только Владелец.
  - **Вывод средств с ИИС теряет налоговый вычет → бот этого не предлагает** (жёсткое
    правило).
- **Скоринг акций** (`/topstocks`): веса Стоимость 22.5 / Качество 22.5 / Рост 20 /
  Дивиденды 15 / Личное 20. Премия = `100/PE − YTM лучшей облигации`. **Акции не
  покупаются** — только шортлист; `/reinvest` покупает только облигации. Логика:
  акция должна бить безрисковую облигацию, иначе смысла в риске нет.
- **Экспорт обезличен** (без `account_id`/`figi`/`uid`/средней цены) ради приватности
  витрины; скруббер роняет вывод при утечке идентификаторов.
- **Два потребителя — две формы данных:** локальный `portfolio_snapshot.json` (v1) —
  вход модуля скоринга; `v2`/`v3` — push в витрину. **v1 ломать нельзя** — на нём
  завязан скоринг.
- **`for_iis_flag` в универсуме — это колонка, а не фильтр:** отдаём весь базовый
  каталог, потребитель фильтрует сам.
- **Монотонный `as_of`** (+1 сек при коллизии) — витрина отклоняет устаревший срез.
- **Fail-closed по quality:** если quality-модуль включён, а его файла нет —
  публикация останавливается, а не выдаёт урезанный market-only снимок за полный.
- **Явный `User-Agent` у публикатора** — Cloudflare режет дефолтный `Python-urllib`
  (см. ниже).

## Что проверено и с каким результатом

- **Экспорт вживую:** universe-прогон — 1921 строка портфеля/каталога, allowlist
  1852, fundamentals 1664, все ok, скруббер прошёл.
- **Push портфеля в витрину:** `accepted (202)`.
- **Скоринг, боевой прогон на Pi:** сухой прогон ~105 строк / 10 секторов / ~237 КБ
  (market-only, ~70 сек); с quality ~254 КБ; публикация — `202 accepted` (после
  фикса User-Agent).
- **Cloudflare `error code: 1010`:** дефолтный `User-Agent: Python-urllib` → **403**
  на обоих маршрутах, ещё до Worker'а. Кастомный UA доходит до Worker (401 без ключа
  / 202 с ключом). Воспроизведено и подтверждено. Это **не** секрет, **не** размер
  тела, **не** IP — именно User-Agent.
- **v3 (снимок портфеля):** 39 оффлайн-тестов зелёные — единицы в долях (`0.1275`, а
  не 12.75), типы купона fixed/floating/unknown, day-count, аномалия
  `maturity < as_of` → `null`, `trailing_12m` → `null`.
  **⚠️ Живого прогона v3 на реальных данных не было** — бот остановлен до деплоя.
- **TLS:** цепочка `russian_trusted` проверена `openssl` — OK.

## Незакрытые хвосты и недоделки

- **v1.1.11 (снимок портфеля v3, dry-run): код готов, но никогда не задеплоен и не
  прогнан на живых данных.** Реального `portfolio_snapshot.v3.json` нет; поразрядная
  сверка купонов по выпускам не сделана.
- **Переключение push v2 → v3 не сделано** — ждёт, пока витрина начнёт принимать v3
  в проде (сейчас v3 только пишется в файл, в push не идёт).
- **`trailing_12m` XIRR = `null`** — нет собственной истории NAV (см. грабли API).
- **`issuer_name` = `null`** — нет поля в API.
- **Автопокупка, отчёт «лотов 0»:** отчёт не перечитывает состояние лимитной заявки
  (метода опроса заявок в клиенте нет) и не печатает план трат. **Первая боевая
  автопокупка на лимитках не подтверждена как FILL** — при первом отчёте свериться,
  что лимитки исполняются, а лимит концентрации срабатывает.
- **Запарковано:** более умный детект налогового вычета в XIRR; штраф скору акции за
  премию E/P без дивидендов; детерминированный `order_id` для безопасного ретрая
  автопокупки.
- **Налоговая подсказка на взносы** отложена до финала прототипа. Read-only оценка:
  взносы = `OPERATION_TYPE_INPUT` за год; возврат ≈ min(взносы, лимит) × 13%.
  Показывать строго как «можно вернуть **до** X» — это **не** гарантия и **не**
  налоговая консультация (типа ИИС и уплаченного НДФЛ в API нет).
- **Скоринг:** фундаментальное покрытие quality пока по одному сектору → баллы в
  витрине в основном пустые; ждёт расширения на стороне витрины/скоринга.

## Миграция HA → Ubuntu: что умерло, что переезжает

Целевая схема: **остаёмся на Docker.** GitHub Actions продолжает собирать
multi-arch образ и публиковать его в ghcr.io; на Ubuntu он запускается через
docker-compose (тег = версия), данные — в volume, автозапуск через systemd или
`restart: unless-stopped`. Пересобирать образ не нужно — умирает **не образ**, а
Home Assistant как способ его запускать.

**Правило разбора:** свойство HA-аддона умирает вместе с аддоном; свойство бота,
API Т-Банка или CI — переезжает.

**Умерло с HA** (умер не образ, а HA как раннер):

- **HA-Supervisor как раннер.** Supervisor тянул образ по тегу, равному полю
  `version` в манифесте аддона (`tinvest_bot/config.yaml`), **а не по `:latest`** —
  поэтому релиз бампили в паре (манифест + теги в `build.yml`). Забыл тег →
  «Обновить» падало, а аддон крутил старую версию. Вместе с этим умерли «Проверить
  обновления» = git pull клона HA-стора и его кэш. На docker-compose тег
  указывается явно.
- **Манифест аддона** `tinvest_bot/config.yaml` (name/version/image/arch/map/boot)
  — точка входа HA-стора; на docker-compose не нужен. Остаётся только
  рантайм-`config.yaml` (настройки бота). Это две **разные** сущности.
- **HA-обвязка в образе** (s6-overlay, `bashio`, `run.sh`, Watchdog, `map:
  share:rw`) физически остаётся в образе, но её HA-часть мертва: `bashio` читал бы
  опции из `/data/options.json`, которого под docker-compose нет. Настройки бот
  берёт из `TINVEST_DATA_DIR/config.yaml` (options-schema в манифесте нет), поэтому
  при переносе стоит проверить, что `run.sh` стартует на env и не падает на bashio.
- Пути `/share/…` — HA-конвенция. Бот читает `TINVEST_DATA_DIR`, так что меняется
  только значение пути + volume.
- Мёртвый груз репозитория: вложенная папка `tinvest-ha-addon/` с тем же slug
  когда-то шэдоуила манифест — просто удалить.

**Переезжает на Ubuntu** (обязательно):

- **CI и образ ghcr:** сборка multi-arch (aarch64 под Pi) в GitHub Actions и
  публикация в ghcr остаются; пакеты держать Public (Docker Hub из РФ отдаёт 403).
- Весь `build/app/` (config, tinvest_client, formatters, telegram_bot, stocks,
  snapshot_export, main) + requirements. Меняется только путь данных.
- RU-IP и Russian Trusted CA (см. «Требования окружения»).
- Вся торговая/read-only логика, автопокупка, расчёт скоринга, экспорт, push.
- Скоринг как отдельный read-only процесс — второй сервис compose или venv.

**Данные для перезапуска:** незаменимы только `.env` (токены) и рантайм-`config.yaml`
(ручная настройка расписаний, лимитов, списков доступа). Всё в `export/` и состояние
скоринга **регенерируются** первым же живым вызовом API. Бот не копил незаменимой
истории (потому и trailing-12m нечем считать). Инвентарь и вердикт о полноте
сохранённого набора — в `CLAUDE.md`.

## Привычки верификации (часть переезжает)

- **Оффлайн-тесты держать при переезде:** `tests/test_snapshot_export.py`,
  `tests/test_push.py`, `build_scoring/tests/`. `FakeClient` не имеет торговых
  методов (их вызов → `AttributeError`); AST-тест ловит торговые вызовы в
  экспортёре; тесты проверяют доли (не проценты), `market_value` из текущей цены,
  работу скруббера.
- **`py_compile` перед стартом** — на HA был гейт в Dockerfile; на Ubuntu держать
  как ручную привычку.
- **Telegram HTML:** символ `<` в тексте молча ломает отправку при `parse_mode=HTML`
  — экранировать.
- **Операционные состояния** (нет средств, рутина) — в лог, лишние Telegram-алерты
  только с явного согласия владельца.
- **Модель работы с торговой логикой:** сначала описать изменение → подтверждение →
  код. Список наблюдателей — только чтение, не расширять.

## Связанные части проекта

- **Витрина Mini App** — один Cloudflare Worker с двумя маршрутами (портфель и
  скоринг), у каждого свой секрет.
- **Модуль скоринга** — отдельный read-only процесс, публикует рыночный профиль в
  витрину.

Смежные рабочие контексты — «штаб» (архитектура проекта) и «Codex» (витрина и модуль
скоринга).
